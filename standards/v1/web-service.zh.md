# Web 后端服务脚手架规范（v1）

tags: service, 脚手架, web, 分层

## 1. 必备工程结构

生成 .NET Web 服务时，优先建立以下清晰边界；项目名称可按业务命名，但职责不得合并或倒置：

- `*.Api`：应用入口、Controller/Endpoint、认证授权、中间件、页面/API 协议适配。
- `*.Bll` 或 `*.Bal`：业务用例、业务规则、流程编排和事务决策。
- `*.Dal`：数据上下文、Repository、查询和持久化实现。
- `*.Model`：实体、DTO、枚举和请求/响应契约。
- `*.Utility` 或 `*.Utils`：图像、Excel、文件、格式转换等跨模块可复用能力。
- `*.Tests`：业务层、数据访问层和接口的针对性测试。

非 .NET 服务也必须创建等价目录边界。不得把数据库访问、业务规则、页面逻辑和通用工具堆到同一个项目、Controller 或大型服务类中。

## 2. 生成前与生成中检查

1. 先输出实施清单：文件树、每个项目职责、每个新增类职责、调用方向和拟复用的 Utility；确认没有重复造已有图像、Excel 或文件工具后再写代码。
2. 每个项目入口、主要类、公开成员、构造函数、方法与复杂分支写中文注释；复杂实现必须注明更简单方案为何不可行及其解决的用户问题。
3. API/页面层只能协调请求与响应，Bll 承载业务，Dal 承载数据库，Utility 承载通用复用能力。发现跨层需求时，应调整到正确项目，而不是在当前文件临时堆代码。
4. 服务必须提供配置读取、统一错误处理、健康检查、README（启动、验证、已知限制）和基于成熟开源日志框架的结构化日志配置；日志输出到项目根目录的 `logs/` 并配置滚动、保留与敏感信息脱敏。

## 3. 交付验证

- 先执行项目既定的格式检查、构建和测试命令；再启动服务并验证健康检查为成功状态。
- 对关键接口至少验证正常输入、非法输入、权限失败和外部依赖失败的返回边界。
- 交付摘要必须列明：项目分层、复用的 Utility、新增类职责、验证证据和已知限制。
- 发布与部署环节遵循 `v1/delivery.zh` 交付与生产纪律规范：验证三件套全绿 → 中文提交推送 → 发布校验 → 暂存验收 → 用户确认后重启生产。
