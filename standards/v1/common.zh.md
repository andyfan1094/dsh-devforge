# 通用开发规范（FhDoc 分层版 v1）

tags: common, 基础, FhDoc, 可读性, 复用

本规范适用于所有服务生成任务。子代理必须在动工前通读并逐条落实；需求与本规范冲突时，先说明冲突并取得确认。

## 1. 先分职责，再写类

- 开始编码前，必须先列出项目/模块边界、每个新增类的唯一职责和调用方向。类、文件和项目不能因为“写起来方便”而混放职责。
- 每个方法只处理一个明确的业务步骤。只有拆分后确实更容易阅读时才提取私有方法；禁止为将来可能使用而预建接口、工厂、抽象层、依赖或实体类。
- 优先选择能正确满足需求的最简单方案。实现前问自己：是否有更简单、可读且可维护的做法？若必须采用复杂方案，必须在实施清单中写清简单方案为什么不能满足，以及该复杂度解决了用户的什么具体问题。
- 优先复用成熟、维护活跃且与项目兼容的开源包：日志、认证、序列化、校验、文件/图像/Excel 处理等通用问题，先检查现有依赖和主流开源实现，避免重复手写。新增包前确认维护状态、许可证、安全风险、平台兼容性和真实收益；不能为了一个简单操作引入重型依赖。

## 2. 中文注释是代码的一部分

- 所有新增或修改的类、公开成员、构造函数、方法及其关键参数都必须有清晰的中文注释；公开 API 使用中文 XML 注释。
- 复杂流程、业务判断、边界条件、异常处理、性能取舍和安全限制必须在代码附近说明业务目的、判断依据和影响范围，不能只在外部文档说明。
- 注释解释“为什么这样做”和“什么情况下不能这样做”，不得逐字重复代码本身。禁止出现只有代码、没有可读业务说明的复杂实现。
- 数据库新增表、字段、索引和迁移必须写中文 COMMENT，说明业务含义与约束。

## 3. 人类可读性优先

- 新增或修改业务代码以初级开发人员能按执行顺序读懂为标准。优先使用清晰的 `foreach`、`for`、`if`、`switch`、具名局部变量和具名布尔条件表达业务流程。
- C# 能写出具体类型时必须使用显式类型声明，避免 `var`；仅匿名类型、匿名数组、`out var` 或解构等无法写出合理类型的场景可以使用 `var`。
- LINQ 只用于短小、单步骤且一眼可读的查询或转换。多个链式操作、业务判断、分组、嵌套查询或复杂空值处理必须拆成具名步骤或普通循环。
- 禁止嵌套三元表达式，避免用难以调试的表达式体、连续空值运算或隐式副作用隐藏业务判断。

## 4. 复用与 Utility 边界

- 写新代码前，先检索同项目和 `Utility/Utils` 层是否已有可复用能力。图像处理、Excel 读写、文件读写、格式转换、通用校验等跨业务能力应复用已有实现；没有时才在 Utility 层新增一次、供各层调用。
- Utility 只容纳稳定、无业务语义、可被多个模块复用的通用能力；不得把订单、用户、发票等领域规则塞进 Utility，也不得把 Utility 当成无边界的杂物箱。
- 仅一个业务流程私有且不具备复用价值的逻辑，应留在所属业务层。复用的目的是真实消除重复，而不是为了抽象而抽象。

## 5. 异常、安全与边界

- 所有外部调用（HTTP、数据库、文件系统、缓存、模型服务）必须有超时、异常处理和可诊断日志；返回给用户的错误应可读但不得泄露内部实现或敏感信息。
- 日志使用成熟日志框架与结构化字段，不手写分散的日志轮转或收集器。应用启动/停止、关键业务开始与完成、外部调用的目标与耗时、数据写操作、鉴权失败、重试、降级和异常必须记录日志。
- 日志文件统一输出到项目根目录的 `logs/`，按日期或大小滚动并保留合理数量；日志目录和日志文件不得提交版本库。严禁记录密码、令牌、完整 API Key、Cookie、连接串、完整身份证明或原始敏感文件内容。
- 输入校验前置：路径必须校验绝对/相对、白名单与目录穿越；所有外部输入均不可信。
- 配置与代码分离：密钥只可来自环境变量或私有配置文件，严禁硬编码、写入文档或提交历史。
- 重复触发同一动作不得产生重复副作用；需要写操作时应设计幂等或去重边界。

## 6. 重构与交付自检

- 仅为可读性进行的重构不得改变接口、数据模型、默认值、异常行为和业务边界，不得顺带修改无关代码。
- OCR 识别、字段比对、金额、日期、文件处理和权限等核心逻辑，改动前后必须用针对性测试或输入输出对比确认结果一致。
- 完成后必须输出交付摘要：职责边界与调用方向、文件清单、启动方式、验证命令（或自测步骤）和已知限制。

## 7. 验证成功后的版本管理

- 目标目录是 Git 仓库，且本地 Git 或已连接的 GitHub/其他版本管理工具可用时，构建、测试和必要验证全部成功后，必须自动为本次任务产生的代码变更创建一次提交。
- 提交前先检查工作区状态，只暂存本次任务新增或修改的文件；不得把用户原有未提交改动、无关文件、`logs/`、私有配置、数据库、密钥、令牌或测试产物带入提交。
- 提交信息使用清晰、简洁的中文，说明类型和实际变更，例如 `feat(识别): 新增发票文件校验` 或 `fix(鉴权): 修复密钥吊销后仍可访问的问题`。
- 验证失败、存在无法区分归属的改动、不是 Git 仓库或没有可用版本管理能力时，不得强行提交；保留改动并在交付摘要中说明原因。
- 自动提交不等于自动推送。除非用户明确要求，禁止执行 push、创建远端分支、标签或 Pull Request。
