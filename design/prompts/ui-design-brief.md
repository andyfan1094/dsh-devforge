# 界面设计需求提示词

> **用途**：当需求只有一句话（「做个后台」「首页再高级一点」）时，先跑这段提示词把方向定下来，**再**动手写代码。
> 它挡住的典型事故：直接开写 → 出来一版"哪儿都对、就是不像这个产品"的界面 → 返工。
> **用法**：整段复制下面代码块，把 `<...>` 换成实际信息，把最后一段一起带上。

## 提示词正文

```text
你是资深产品设计师。按以下顺序产出，不许跳步，不许写代码。

1) Design Read —— 一段话，3 到 5 句，必须回答：
   这是什么产品、给谁用、在什么场景下被看见、应该给人什么感觉、最不该像什么。

2) 三旋钮定档 —— 各给 1 到 5 的档位，每个档位配一句理由（不许只报数字）：
   DESIGN_VARIANCE（版式偏离常规的程度）
   MOTION_INTENSITY（动效强度）
   VISUAL_DENSITY（信息密度）

3) 内容真值 —— 列出这个页面必须承载的真实内容单元。
   每条写清"它是什么"和"它回答用户的哪个问题"。
   禁止出现「卡片一」「功能二」「Feature A」这类占位。

4) 视觉方向 —— 一句话定调，并给出选定的设计系统 id（形如 systems/<id>）与选择理由。
   说明它为什么配得上这个产品，而不是"看起来专业"。

5) 结构 —— 从上到下的区块清单。每块写：作用、信息优先级、与其他块的关系。

6) 验收线 —— 3 到 6 条"做到才算过"的可判定标准。
   必须包含：桌面与移动两档的自检要求，以及 加载 / 空 / 错误 三态的处理方式。

7) 已知风险 —— 这版最容易做砸的一处，以及规避办法。

输入信息：
<粘贴用户原始需求、产品背景、目标用户、参考对象、硬性约束>

约束：
- 不确定的信息标注「待确认」，绝不编造指标、客户名、数据或引用。
- 不要给三个以上备选方案；给一个主推方向，并说明它主动放弃了什么。
- 不许出现「赋能」「一站式」「极致体验」这类无法验收的词。
```

## 输出怎么用

| 产出项 | 下一步动作 |
| --- | --- |
| Design Read | 写进交付说明开头，是后续所有取舍的理由来源 |
| 三旋钮档位 | 直接决定间距、动效时长、每屏信息量的取值区间 |
| 内容真值 | 变成页面里的真实文案，杜绝占位填充 |
| 选定的 systems id | 读该系统的 `tokens.css`，颜色间距字体一律走 token |
| 验收线 | 交付前逐条打钩，配合截图自检 |

## 常见误用

- **跳过 Design Read 直接要结构**：结构是从调性推出来的，顺序反了必然返工。
- **三旋钮全给 3**：全中间档等于没有方向，说明还没想清楚这个产品该偏哪边。
- **把「待确认」当通过**：涉及真实数据口径的待确认项必须回头找用户，不能自己填。
