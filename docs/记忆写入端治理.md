# 记忆写入端治理（0.53.0–0.54.0）

记忆库膨胀的治理分两层：**存量清理**（一次性，见 2026-10-18 全量审阅）与**写入端治理**（本文）。
只做存量清理是治不住的——清理完当天，候选域又长回 837 条 / 3.04 MB，证据 6.85 MB / 15459 条。
所以真正的修复点在写入端：让垃圾**不再被写进来**，而不是写进来之后再扫。

## 一、问题定位：体积到底花在哪

对生产库做逐域拆解（86.20 MB 时）：

| 位置 | 体积 | 说明 |
| --- | --- | --- |
| `memory.entry` 正文 | 2.21 MB | 真正的记忆内容，占比极小 |
| `memory.candidate` | 17.40 MB | 6065 行，6057 条 `auto-activated`，**无任何清理路径** |
| `memory.meta.evidence` | 13.04 MB | 占 meta 域 15.23 MB 的 86%，原始工具输出永久保存 |

结论：膨胀从来不是「记忆条数太多」，而是**两份冗余副本**：

1. 候选被采纳后，那份 5000+ 字节的全文副本被永久保留，没有任何 TTL 或裁剪路径。
2. 证据里存的是工具输出原文，24799 条证据中 13584 条是长引文，但**只有 2591 种唯一文本，最高重复 121 次**。

对候选再做一次字节级拆解（837 条存活 / 3.67 MB）：

| 字段 | 占比 | 单条 |
| --- | --- | --- |
| `evidence` | **77.9%** | 3577 B |
| `content` | 4.8% | 219 B |
| `reason` | 2.2% | 99 B |
| 其他 | 15.2% | 699 B |

也就是说候选膨胀的**八成来自证据**，而证据在激活时已经随 `entryInput` 写进 `memory.entry` 了——
候选里那份纯属重复。这是本次最关键的发现。

## 二、四处改动

### 1. 候选墓碑化（`governance.pruneResolvedCandidates`）

终态候选（`approved` / `auto-activated` / `rejected` / `deduped`）超过保留期后压缩成墓碑：
只保留 `id` / `state` / `resolvedAt` / `createdAt` / `resultEntryId` / `duplicateIds` / `source`
七个对账字段，丢掉 `content` / `evidence` / `tags` / `scope` / `reason`。

- **不删除**：保留「这条候选后来对应哪条记忆」的可追溯性。
- **只碰终态**：`pending` / `needs-resolution` 是等用户裁决的活数据，绝不压缩。
- **节流**：每 20 次 `propose()` 触发一次（候选只在那里增长，与 audit 域 0.43.0 的修法一致）。
- **幂等**：墓碑行 `typeof data.content !== 'string'`，`parseCandidate` 直接返回 `undefined`，
  自然不再出现在候选列表与 `quality()` 统计里，重复执行返回 0。

保留期**实测调参**（生产日增 817 条、单条 4594 B）：

| 保留期 | 稳态行数 | 稳态体积 |
| --- | --- | --- |
| 3 天 | 2451 | 7.80 MB |
| 1 天 | 817 | 2.60 MB |
| 6 小时 | 204 | 0.65 MB |

最初定 3 天等于没改善，最终取 **1 天**：既有当天可追溯性，稳态又回到可用区间。
保留期只影响「刚采纳的候选还能不能翻全文」，而正文本来就落在 `memory.entry` 里。

### 2. 激活时不再落证据（`governance.activateAuto`）

证据已随 `entryInput` 写进 `memory.entry`，候选副本不再重复保存。
内存返回的对象仍保留完整证据，**调用方语义不变**；只有持久化副本瘦身。
单条体积 4594 B → 约 1000 B。

### 3. 证据引文截断与去重（`sediment.ts` / `native.ts`）

- `EVIDENCE_QUOTE_LIMIT = 200`：引文只存前 200 字，不再整段保存工具输出。
- `dedupeEvidence()`：按 `digest`（无 digest 时按引文文本）去重，同一段引文只留一份。

### 4. 低价值内容过滤（`sediment.isLowValueMemory`）

**刻意做窄**。初版用宽模式（P 编号+完成动词、耗时+通过）在生产 3875 条活跃记忆上回放，
命中 22 条，其中 **12 条是误报**：

- 记录归档规则本身的记忆（"任务播报（P0-P4 编号、已修复宣告）应归档"）被自己的规则命中；
- 「junhui-model 已纳入服务器管理体系，winrm_test 耗时 808ms 通过」这类真实事实被误判。

按真实数据观察到的分界重构后，只保留两个强信号：

- 同一短句里「任务编号 + **真实行号引用**」（规则说明不会写具体行号）；
- `N/N` 形式的测试通过数。

长文档与多行内容一律放行（含标题 / YAML 头 / 章节列表的内容里，编号与状态词是文档正文的一部分）。
状态词（未提交 / 待验收）判定同样加长度守卫。

**提示词才是主防线**，机械过滤只是兜底。回放结果：**22 条 → 0 条误报**。

## 三、顺带修掉的两个真实缺陷

1. **`memory_manage update` 被自身误判重复**：`propose()` 的包含式比对会匹配到正在更新的那条自己，
   报「更新后内容与现有记忆重复，未落盘」。修法：`MemoryCandidateInput.excludeEntryIds`，
   tools.ts 更新路径传入 `[current.id]`。
2. **`quality()` 待审计数封顶在 1000**：原实现走 `listCandidates({limit:1000})`，
   而该方法 `Math.min(1000, …)`。修法：改为直接统计域内行数。

## 四、验证

- **单测 911 例全通过**（`node --experimental-strip-types --test tests/*.test.ts`），`tsc --noEmit` 干净。
  新增 `tests/memory-writepath.test.ts` 15 例，覆盖墓碑化 5 例、quality 计数、证据去重 2 例、
  截断、低价值过滤 4 例、激活瘦身、excludeEntryIds。
- **暂存真实数据回放**：2210 条终态候选 → 2.35 MB 降到 0.54 MB（**−77%**），第二轮 0 条（幂等）。
- **生产实机探针**（运行中的 0.54.0，走 `/memory/save`）：送入 600 字引文落盘 **200 字**；
  送入 3 条（2 条同 digest）落盘 **2 条**。验证后探针已删除，残留 0。
- 生产重启后：`active 3880 / archived 2481 / candidates 0 / conflicts 0`，库 52.41 MB，
  `PRAGMA quick_check = ok`。

## 五、需要知道的代价

- 候选超过 1 天后，面板里只剩对账记录，看不到正文（正文在记忆条目里，不影响召回）。
- 证据按 digest 去重后，若某条 meta 的后期证据与早期证据重复，会丢掉重复的那一份。
- 机械过滤宁可漏也不误伤：单次耗时播报（"构建耗时 38.8 秒"）这类不会被拦，交给提示词约束。
- 存量数据不会被改写，只对新写入生效。生产重启时那 842 条存量候选仍在 1 天保留期内，
  过期后由节流器自动墓碑化。
