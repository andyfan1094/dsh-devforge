# 知识库写入工具 kb_manage（0.60.0）

本文档说明 0.60.0 新增的模型工具 `kb_manage`：它为什么存在、能做什么、哪些库不许写、以及写错了怎么回滚。

## 一、为什么要加这个工具（真实事故）

2026-10-19 辉哥发现知识库里有一条文档内容已过期，问模型能不能改。模型的回答是：

> 那条知识库文档是只读的、无法改写……哪天它自动刷新就一致了。

这句话两半都是错的，而且错得各有各的原因：

| 模型的说法 | 实际情况 |
| --- | --- |
| 「那条文档是只读的」 | 阅读器并没有只读标记。真正的原因是**模型侧没有任何工具能写知识库文档**——只能说"我改不了"，它把"我没工具"说成了"这文档只读"。 |
| 「哪天它自动刷新就一致了」 | 那句话所属的知识库是人工库（`source=manual`），**全仓库没有任何代码会刷新它**（`grep 历史文档` 在 `src/` 下零命中，镜像同步只认「Mnemon 镜像」「Hindsight 镜像」两个库名，且外部镜像源目录当时已经不存在）。这句是模型自己补的理由，方向还说反了——它把"没人管"说成了"有人会来管"。 |

根因不是模型笨，是**工具面缺了一块**：在此之前模型侧与记忆中枢相关的工具只有两个——

- `rag_search`（`src/rag/tools.ts`）：纯检索，只读；
- `memory_manage`（`src/memory/tools.ts`）：只写内置长期记忆（`memory.entry`）。

而知识库文档（`rag.doc`）**在工具面上完全没有写入路径**。写在文档里的东西偏偏会过期，模型于是只剩"编理由"这一条路。

`kb_manage` 就是把这条路补上，并且顺手把"哪些库能写、为什么不能写、该去哪改"变成工具的真实返回值——让模型再没有编造理由的空间。

## 二、能做什么

| action | 作用 | 关键参数 |
| --- | --- | --- |
| `list` | 列全部知识库：id、名称、来源、**是否可写**、文档数 | 无 |
| `docs` | 列某库文档：docId、文件名、状态、切块数、源文件路径 | `kb` |
| `read` | 读回文档正文（默认 12000 字窗口，可 `offset` 续读，单次上限 40000 字） | `docId` 或 `kb`+`fileName` |
| `ingest` | 写入文档，**同名即覆盖**（这就是"修正文档"的正确姿势） | `kb`、`fileName`、`text`（整篇正文） |
| `delete` | 删除文档（删前留快照） | `docId` 或 `kb`+`fileName` |
| `restore` | **用快照把文档写回原样**（覆盖写了错的、误删了的，都能救回来） | `backupId` |

`kb` 参数接受知识库 **id 或名称**；名称要求完全相等且**唯一**，同名多个会明确报歧义并要求改用 id（不静默取第一个，否则同一串参数换个创建顺序行为就相反）。

**所有库都可读，只有 `source=manual` 的库可写。**

## 三、写权限护栏（红线）

**只有 `source=manual` 的库允许写入。** 其余三类库一律拒写，并回明确原因与正确处置：

| 库来源 | 正文由谁决定 | 拒写时告诉模型什么 |
| --- | --- | --- |
| `manual` | 人（面板上传 / 本工具） | ——可写 |
| `project` | 项目索引器，按本机项目目录生成（白名单扩展名） | 改副本会在下次索引时被源文件覆盖、源文件删了或被移出索引的文档也会被清掉；**请改源文件**（用 `docs` 看 `sourcePath`）后重新索引 |
| `mirror` | 外部源（Mnemon／Hindsight）单向拉取 | 改副本会在下次镜像同步时被覆盖、源侧消失的文档也会在同步时被清掉；**请改外部源**，再等同步或手动同步 |
| `memory` | 历史会话记忆沉淀的产物 | 当前沉淀层写入的是**内置长期记忆（`memory.entry`）**，此库不再有新内容（也可能是统计模块刚建出来的空库）；要纠正长期事实**请用 `memory_manage`** |

> **`memory` 归因的订正（2026-10-19 独立复审发现，原文案是错的）**
> 本条最初写的是"该库正文由会话记忆沉淀层写入"。代码层这句话**曾经**为真，但**当前接线下已是死代码**：`sediment.ts` 里那条 `ingestText(kbId, fileName, text, { source: 'memory' })` 位于 `if (this.governance !== undefined) { … continue }` 分支之后（`sediment.ts:476` 与 `:505-511`），而 `index.ts:930` 确实注入了 `governance` → 该分支永远先命中并 `continue`，RAG 的 memory 写入不再执行。
> 实时数据也印证：生产 `会话记忆库`（`source=memory`，id `acd7542f-b3ca-4138-b9af-d12510dddaac`）共 74 篇文档，**最后一篇创建于 2026-09-03**，在主机持续运行的情况下六周无新增。
> 旧文案会让模型以为背后有个活跃写入方，属于"自信地说错机制"——正是本文档开头那个事故的同一类缺陷，故改掉。

设计要点：拒写理由不是"你没权限"这种无信息量的话，而是**把该去哪里改说清楚**。否则模型只会换个措辞继续猜——这正是事故里发生的事。

护栏优先级：`delete` 会**先按 `kb` 判定护栏、再去找文档**。这样即使模型把文件名猜错、或库里根本没这条文档，它拿到的仍然是"这个库归 XX 管、该去 YY 改"，而不是"未找到文档"（后者会让它以为是自己名字写错，换着文件名反复试）。

未知 `source`（将来新增类型）走中性兜底文案，不会被硬说成某一类。

## 四、安全装置

| 装置 | 说明 |
| --- | --- |
| 覆盖前快照 | 同名覆盖前，把原文存进 `rag.backup` 域（`text` + `docId` + `fileName` + `reason` + `at`），返回 `backupId` 给模型 |
| 删除前快照 | 删除不可逆，同样先存 `rag.backup` 再删 |
| **可回滚** | `restore` + `backupId` 即可把文档写回（覆盖、误删都适用）。回滚本身也是一次写入：目标库仍须存在且仍属 `manual`，否则同样拒写；回滚前也会为"当前内容"再留一份快照，故回滚同样可逆 |
| 内容未变短路 | 要写的正文与库中 `contentHash` 一致时直接返回 `mode=unchanged`，不留快照、不记写审计、不重嵌向量 |
| 写审计 | 每次写入/删除/回滚记一条 `rag.audit`（`actor`、`action`、`result`、`kbId`、`fileName`、`docId`、`textChars`、`backupId`、`at`）。**只记元数据，绝不记正文**；只保留最近 500 条（`KB_AUDIT_KEEP`）。**失败也留痕**（`result=failed` + 截断的错误文本），否则事后分不清"没写"与"写了但失败" |
| 快照保留上限 | `rag.backup` 只保留最近 200 条（`KB_BACKUP_KEEP`），按时间删最旧。必要性：单条快照上限 200000 字，而 `store.db` 会被 CNB 加密备份整体打包推送，无上限会持续膨胀备份体积 |
| 写入频率闸门 | 60 秒窗口内最多 10 次写入（`WRITE_WINDOW_MS`／`WRITE_WINDOW_MAX`），防模型循环批量改写；被拒的调用不消耗配额；**写入与删除共用该配额**（拒绝文案已写明） |
| 歧义拒绝 | 同名知识库、同库同名文档都不静默取第一个，而是报错并要求改用 id／docId |
| 规模上限 | 单篇正文上限 200000 字（`INGEST_MAX_CHARS`）；单次 `docs` 列出上限 200 篇（超出显式告知截断数，并提示"未列出不等于不存在，可直接用 read 指定 fileName"） |
| 参数校验 | 文档名须单行、非空、≤200 字符；正文不可为空；`read` 偏移超出正文长度时明确报错而不是回空正文 |

## 五、读回正文的口径（重要边界）

`read` 返回的正文由**索引切块按绝对行号重建**，不是上传前的原始字节：

- 切块入库时做过 `trim`，因此**块首尾空白会被规范化**（独立复审实测：40 行 4 空格缩进文本 1989 字 → 重建 1969 字，丢 20 字，正好落在 5 个切块的边界行；CRLF、多节 Markdown、超长单行均不丢行）；
- 之所以不直接拼接切块，是因为相邻切块带 `overlap`（默认 64 字）重叠区，直接拼接会把重叠内容重复一份——而模型拿到正文后往往整篇回灌，重复内容会被真的写回库里。按行号重建可让重叠区自然幂等覆盖。

因此工具结果里带了明确提示，**且该提示排在正文之前**（读完正文才看到就晚了）：

> （本正文由索引切块按行号重建，块首尾空白可能被规范化。要整篇重写请以你自己的源文本为准，不要直接回灌本返回值。）

回归用例专门锁两件事：200 行长文必然多切块，断言读回正文与原文**完全相等**、长度一致；以及缩进类文档的渲染里必须**前置于正文**带出上述提示。

## 七、独立复审修掉的缺陷（2026-10-19）

交付前由独立 teammate 做了对抗性复审（只读，不改仓库），实测 11 项、其中核心护栏全部成立（含 delete 只给 docId、kb 与 docId 指向不同库、非 manual 覆盖等绕过尝试均被挡；闸门无并发穿透）。本轮据此修掉：

| 缺陷 | 修法 |
| --- | --- |
| 「可回滚」是空头承诺：只写快照、全仓库无任何写回入口 | 新增 `restore` action，让承诺变成真的 |
| `memory` 库拒写理由归因已过期（见第三节订正框） | 改口径并加未知 source 中性兜底 |
| `mirror` 拒写文案只提"覆盖"，漏了"源侧消失的文档会被清掉" | 补上 |
| 同名知识库静默命中第一个 → 可能按错误理由引导模型去"改源文件" | 报歧义错误，列出候选 id |
| 同库同名文档静默删错一条 | 报歧义错误，要求用 docId |
| 覆盖写入失败时留了快照、没留审计 | 失败路径补 `result=failed` 审计 |
| 幂等重写也照记"覆盖"、白留快照与审计 | 比对 `contentHash`，一致则短路为 `unchanged` |
| `rag.backup` 无上限且正文随 `store.db` 进 CNB 加密备份 | 加 `KB_BACKUP_KEEP=200` 裁剪 |
| `read` 的重建提示排在正文之后 | 前移至正文之前 |
| `docs` 截断后 read 报"未找到文档"，无法分辨"真没有"与"没列出" | 截断提示里写明可直接用 read 指定 fileName |
| `read` 越界偏移返回空正文且 `truncated=false`，易被误读为"文档是空的" | 明确报错并给出正文总长 |

（复审同时确认无需改动的部分：`project` 拒写文案与索引器实际行为一致；审计不会无限膨胀；审计不落正文；CRLF／多节 Markdown／超长单行不丢行；闸门被拒不消耗配额、并发无穿透。）

## 八、已知限制

1. **只能改副本**：本工具改的是知识库里的文档。若某条事实的真正事实源是内置长期记忆，纠正它应当用 `memory_manage`——工具会在 `memory` 库上明确拒绝并这样引导。
2. **回滚入口只在工具层**：`restore` 已可用，但面板/运维 SQL 尚未做图形入口（`rag.backup` 仍可用 SQL 直接查，见下）。
3. **重建正文的空白边界**：`read` 的回灌不是字节级往返，缩进类文档存在按切块边界丢空白的可能（见第五节）。已在工具输出里前置警告，但未做（也不打算做）字节级保真——那需要改切块存储结构。
4. **不改注入口径**：本次只加了工具（辉哥选定的方案），没有改记忆工作流注入里"查已注入记忆 → 修正过时记忆"的既有表述。工具本身已在描述里讲清分层。

### 附：手工查快照的 SQL（只读）

```sql
-- 1) 找快照
SELECT id, json_extract(data,'$.fileName'), json_extract(data,'$.reason'), json_extract(data,'$.at')
FROM docs WHERE domain = 'rag.backup' ORDER BY sort_order DESC LIMIT 20;
-- 2) 取回原文
SELECT json_extract(data,'$.text') FROM docs WHERE domain = 'rag.backup' AND id = '<backupId>';
```

正常情况下不需要它——直接把 `backupId` 交给 `kb_manage` 的 `restore` 即可。
