# 记忆引用与轮末自评修复（0.59.0）

两个能力一起交付，因为前者是后者的前提：**模型引不到具体某一条记忆，就说不上「修复哪一条」**。
本篇说明它们各自解决什么问题、边界在哪、以及为什么这么设计。

## 一、为什么做这两件事

### 1. 注入的记忆此前无法被引用

每轮会话会把命中的长期记忆注入到上下文里，但注入行的格式只有
`[日期 · 来源 · 类别] 正文` —— **没有任何标识**。

后果很具体：模型读到一条已经过时的记忆，想纠正它，只能说「请把那条讲某某的记忆改掉」。
`memory_manage` 的 `id` 参数要的是完整 UUID，而模型手上根本没有。于是：

- 想修正 → 只能靠复述正文去猜，改错条目的风险很高；
- 想反馈/删除 → 同样无从下手；
- 工作台上看到的问题条目，和模型在上下文里看到的东西对不上号。

### 2. 沉淀只新增，从不回头纠错

沉淀（`sediment`）负责把一轮对话里的新事实写进库，但它**只写不改**。
一条写错的、或环境已经变了的记忆，一旦被注入，就会一轮轮被模型当成事实使用并据此行动，
错误被放大到工具调用里，却永远没有人来纠正它。

`curator`（治理建议）和 `dream`（做梦整理）能处理一部分，但它们关注的是重复与合并，
不针对「这条记忆被本轮对话证伪了」。

## 二、短 ID 引用

### 格式

三条 native 注入层统一为：

```
[2026-09-04 · mnemon · general · #0f327539] 正文
```

短 ID 取完整 UUID 的**前 8 位十六进制**（`SHORT_MEMORY_ID_LENGTH = 8`）。

### 为什么是 8 位而不是完整 UUID

注入预算是硬约束：常驻钉选 600 字、项目档案卡 1800 字。完整 UUID 是 36 个字符，
每条多出 28 字符，在预算不变的前提下会**把正文挤出去几条**。
8 位在碰撞概率与预算占用之间取得平衡——按生日问题估算，约 6400 条时才出现约 1% 的碰撞期望。

### 解析规则（三段式，顺序不可换）

`memory_manage` 的 `get` / `update` / `delete` / `feedback` 都接受短 ID：

1. **完整 id 精确命中优先** —— 老路径零回归，完整 UUID 永远走原逻辑；
2. **前缀扫描全库** —— 支持 8 位短 ID，也支持补更多位数（4 位也行，只要唯一）；
3. **歧义不猜** —— 0 条报「当前作用域内记忆不存在」；多条报「匹配到 N 条，无法唯一定位，
   请补更多位数」，**只给数量不泄漏完整 id**。

空字符串被显式拒绝：否则 `startsWith('')` 会匹配全库，等于把「空参数」变成「命中一切」。

### 顺带补齐的疏漏

`memory_manage` 的 `list` / `search` 输出此前也不带 ID。只调 `list` 的会话拿到的是「无 id 的正文」，
等于把注入行加 ID 的收益丢掉一半。现在列表项形如：

```
1. [#0f327539] [general] 正文…
```

工具纪律文本（每轮注入的行为约束）也补了一条，明确告诉模型「#后面的 8 位就是 id，可直接用」——
不写明的话，模型不会意识到那串东西能当参数用。

## 三、轮末自评修复

### 工作机制

每轮 `turn/end` 时，用**本轮真实对话**复查**本轮真正进入上下文的那几条记忆**。

- 数据源不需要新建：召回轨迹（`memory.recall` 域）本来就记录了 `sessionId`、`turn`、
  以及每个命中项的 `entryId` / `layer` / `included`。取 `included === true` 且 `layer === 'native'`
  的条目即为本轮真正被模型看到的记忆。
- `mirror` 层的 `entryId` 是 chunkId，不是 native 记忆，**必须排除**。

提示词的核心是保守：**只依据本轮对话里真实出现的证据判断，没有证据就 keep**。
把一条正确的记忆改错，比漏掉一次修正严重得多。

### 四种处置

| 动作 | 实现路径 | 是否可逆 |
| --- | --- | --- |
| `update` | `native.update(id, {content})`，带 `updatedAt` 乐观锁 | 版本号前进，可再改 |
| `outdated` / `incorrect` | `governance.submitDirectFeedback` | 隔离 + 负记忆层，工作台可恢复 |
| `duplicate` / `archive` | `native.archive(id, true, 'selfrepair')` + 负记忆层 | **软归档**，工作台可恢复 |
| `keep` | 不产生任何写入 | — |

为什么 `archive` 不用 `submitDirectFeedback`：它只在 `outdated`/`incorrect` 时写负层，
拿它表达「已归档」会走 outdated 分支、让质量统计里的过时数虚高。直接写负层（`kind: 'rejected'`，
id 沿用 `neg-` + entryId，重复触发不堆多条）既精确又同样可逆。

### 安全边界（"全自动" 的前提）

辉哥的决策是**全自动含删除、每轮都跑**。在这个前提下加了几道闸门，
因为「自动删除」一旦失控是不可逆的体验事故：

1. **删除一律是软归档**，绝不物理删除，工作台可恢复；
2. **单轮爆炸半径双限额**：总动作 ≤ `selfRepairMaxActions`（默认 5）、归档 ≤ `selfRepairMaxArchive`（默认 2），
   超出部分丢弃并在审计里记明丢弃数量；
3. **钉选条目永不自动归档** —— 命中钉选只记一条反馈意见，库状态不动。
   理由：钉选是用户显式钉下的硬规则，轮末自评不该有权删；
4. **轮次精确匹配**，不做相邻轮补偿 —— 否则会拿本轮的证据去改上一轮注入的记忆，
   在用户关掉自动注入而旧轨迹还在时会每轮重复审阅同一批陈旧记忆；
5. **同一 id 只应用第一条动作** —— 模型既说 update 又说 archive 时，全放行会让刚更新的正文立刻被归档；
6. **全程吞异常** —— 自评是旁路增强，失败只影响自己，绝不打断会话收尾。

### 成本

只有同时满足「本轮确实注入了记忆 + 有对话文本 + 单轮动作上限 > 0」才调模型。
注入为空、开关关闭、无对话窗口、上限为 0 这四条路径都是**零模型调用**。
按默认上限，每轮最多 1 次模型调用。

## 四、可观测性

自评是唯一会自动删记忆的能力，**跑没跑必须看得见**。

`/api/dsh-devforge/memory/status` 增加 `selfRepair` 观测块，面板记忆页增加「轮末自评修复」状态卡：

```json
{ "attemptCount": 1, "updateCount": 0, "feedbackCount": 0, "archiveCount": 0,
  "skipCount": 0, "failureCount": 0, "lastError": "", "lastOutcome": "no-change" }
```

`lastOutcome` 取值与含义：

| 取值 | 含义 |
| --- | --- |
| `disabled` | 开关关闭 |
| `no-injected` | 本轮没有可审的记忆（最常见，零开销） |
| `actions-disabled` | 单轮动作上限为 0 |
| `no-dialog` | 本轮没有对话文本，无证据可依 |
| `parse-failed` | 模型输出无法解析为动作数组 |
| `no-action` | 模型返回了空动作数组 |
| `no-change` | 模型审阅后判定无需改动（全是 keep） |
| `applied` | 真的改写了库 |
| `failed` | 执行异常（已吞掉，不影响会话） |

未接线时该字段为 `null` 而不是 0：「没接线」和「跑了 0 次」是两件事。

**`no-change` 是实测后补上的**：原实现只要模型返回了动作就置 `applied`，
但全部 `keep` 时库里一条没变，面板会长期显示「已应用」。
这个 bug 是被后加的可观测性用例抓出来的，不是读代码发现的。

## 五、验证

### 自动化

- 新增用例 32 个：注入短 ID 8 个 + 自评 24 个（含 2 个可观测性契约用例）；
- 全量 `968/968` 通过，`tsc --noEmit` 干净。

### 暂存实例实机（隔离 HOME `~/.dsh-staging` + 3081，已禁桌面宠物与飞书桥）

- **注入行带短 ID**：真实会话上下文里为
  `[2026-09-04 · mnemon · general · #0f327539]`，与召回轨迹 `entryId 0f327539-…` 前 8 位一致；
- **自评真的每轮跑**：驱动真实两轮后 `attemptCount = 1`、`lastOutcome = no-change`、`failureCount = 0`；
- **轮次匹配正确**：召回轨迹 `turn = 1 / 2` 与实际驱动轮次完全对应，
  证实 `agent/pre-step` 的 `payload.turn` 与 `turn/end` 的 `data.turn` 是同一套计数器，不存在差 1；
- **面板状态卡渲染正常**，悬停显示「最近判定 + 各类计数」。

### 顺带修掉的一个真漏洞

`native.ts` 的 `asMeta()` 读回白名单漏了 `'selfrepair'`。
类型联合与 `archive()` 形参都加了，却漏了这一处解析 —— 结果是**写得进去、读不出来**：
`get` / `getMeta` / `list` / `listArchived` 全部走 `asMeta`，面板「归档来源」永远显示不出自评归档，
正是 0.51.0 加 `archivedBy` 想解决的那个问题。由线B 在联调中发现并上报。

## 六、已知边界

- **短 ID 碰撞**：约 6400 条时出现约 1% 的碰撞期望。撞了就报歧义、要求补位数，不会猜错；
  前缀扫描依赖 `listAll` 的 10000 行上限（当前库约 6000 行，2 倍余量）。完整 UUID 路径不受影响。
- **自评共识被低置信度模型污染**：提示词已强制要求指向本轮具体证据，但仍依赖模型判断。
  若发现误改，把 `selfRepairMaxActions` 调到 0 即可整体停用自动改动（保留注入统计）。
